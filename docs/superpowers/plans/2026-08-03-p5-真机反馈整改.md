# P5：真机反馈整改 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> to implement this plan task-by-task.

**Goal:** 消化 2026-08-03 真机试用的九条反馈（见
`docs/superpowers/specs/2026-08-03-p5-真机反馈清单.md`），
让 WebUI 从「能打开」变成「能真正把一个直播间配起来并跑起来」。

**Architecture:** 分六批。P5-1 优先，因为它当前**卡死用户自测**——
改任何绑定都要人工重启进程。

**Tech Stack:** 不变。Go 1.25 + PostgreSQL（pgx）+ 标准库 `http.ServeMux`；
Vue 3 + TS + Naive UI + Pinia + Vitest。

## Global Constraints

- 纯 Go 无 CGO，**不引入任何新依赖**；前端同理不加新依赖
- HTTP 只用标准库 `http.ServeMux`，**禁止第三方路由 / 中间件 / Web 框架**
- **一切改变状态的接口不得用 GET**（认证靠 `SameSite=Lax` Cookie 替代 CSRF token）
- 「不存在」与「对调用者不可见」必须返回相同的 404（防枚举）
- 权限点只在 `internal/perm` 定义；所有者旁路只有 `perm.OwnerBypass` 一处
- 金额单位后端一律 **1/100 电池**；**元 = 原始值 / 1000**，换算只在展示层
- 注释写「为什么」不写「是什么」，中文
- 测试：`-count=1`；后端存储测试必须设 `MAGICD_TEST_DATABASE_URL`
  （不设则整包 skip 且退出码 0，是假绿）
- 竞态检测现已可用：`CGO_ENABLED=1 go test ./... -race -count=1`
  （本机 `CGO_ENABLED` 默认 0，必须显式打开）
- **测试写了不等于生效**：本项目已出现过三种「测不到东西」的形态——
  绕开真实时序、前提不成立、断言方向选错。每写一条防护性测试，
  实际删掉那个防护跑一次，确认它真的会红

## P5-1 运行期绑定生命周期（最高优先级，当前卡死用户）

**问题**：`magicd run` 启动时装配一次绑定，此后 `roomRuntime.Reload` 只按
`bindingID` 找**已存在**的运行时。新增绑定不会被拾取，必须重启进程；
而 WebUI 里没有任何地方能重启。真机日志已确认：进程 `绑定数=0` 启动后，
用户在 WebUI 加了账号与绑定，日志此后一条没动。

**要做**：绑定的**新增 / 删除 / 启用 / 停用**在运行期生效，不需要重启。

- 运行时集合从「启动时装配一次的切片」改成可增删的注册表
- 新增绑定 → 建连接、装配规则、注册定时任务；删除 / 停用 → 反向拆掉并断连
- 拆除路径必须干净：连接、goroutine、定时任务、业务日志 Sink 都要收
  （P4-4 已经在「PK 结束断干净」上踩过一轮，同样的四条路径都要有测试）
- **第二个 bug 一并修**：保存成功但重载失败时没有清 dirty 标记，
  导致点了保存右上角仍显示「有未保存的改动」、离开页面还提示未保存

**验收**：WebUI 里加一个绑定 → 不重启进程，日志出现「已连接直播间」。

## P5-2 部署与可观测

- **1a 初始密码**：`.env` 里加必填的管理员初始密码项，不填就启动失败并说明原因。
  现状「只在容器内打印一次」对无头设备极不友好。
- **1b 开播状态**：账号与直播间页显示**主播开播状态**，心跳 **60 秒**
  （现状是 10 分钟被动轮询，页面上写着「还没有被检测过」）。
- **2 即时检测**：扫码完成后**立即检测一次**账号可用性；
  房间添加后**立即检测一次**直播间，并显示**主播 UID（不是房间 UID）与主播昵称**，
  避免加错房间号却要等十分钟才发现。

## P5-3 WebUI 结构

- **3 配色**：登录页外层白、卡片黑，不一致。统一成一种。
- **4 / 5 选择器**：**除首页（账号与直播间）外，每个页面都要「账号 + 直播间」
  选择器**——每个直播间独立配置，不能泛泛。这是覆盖全部页面的结构性改动。

## P5-4 规则语义（两处 radio 实为两个独立开关）

- **5 进房欢迎**
  - 粉丝牌等级筛选改成**独立勾选**，不勾即不启用
  - 筛选条件**叠加**（AND）：粉丝牌等级 + 只欢迎大航海 = 两者都要满足
  - **「窗口合并」与「用户去重」不是二选一**：独立计算、效果叠加
  - 欢迎语模板处补**变量说明**
- **6 礼物答谢**
  - **「多人多礼物合并」与「同一用户礼物叠加」是两个独立开关**，不是 radio
  - **单人优先**：滑动窗口内先挑出「该单独答谢的人」，剩下的零散礼物才并成多人条
  - **单人判定标准：按件数**，窗口内某人礼物总件数 ≥ N 就单独答谢，
    **N 可配、默认 3**（用户 2026-08-03 裁决）
  - 单人累加**跨礼物合并**（盲盒仍单算）
  - 变量说明重写——用户原话「又带点又顿号的到底什么语法」
- **8 其他答谢**：每一条都要有**轮询 / 随机**开关

## P5-5 PK 与串门

- **7a** PK 播报补**变量说明**
- **7b** 串门播报加三个子项：只欢迎对面主播粉丝牌的用户 /
  只欢迎对面粉丝牌 X 级以上 / 只欢迎对面大航海（舰长 / 提督 / 总督）
- **7c 串门判定改成动态**：不能只用 PK 接通那一瞬间的冻结快照
  （**PK 播报保持一瞬间不变**）。改用对面房间**高能榜过去 10 秒的滚动窗口**——
  手机观众不会同时待在两个直播间，串门存在「退出再进」的延迟。
  仓库已有 `cmdmap/onlinerankv3.go`，对面连接本来就收 `ONLINE_RANK_V3`，
  数据源现成。
  - ⚠️ 这会再次改动「观众集合」的语义。P4-4 已经因为「6a 把冻结快照改成实时
    更新、6b 仍按冻结语义写谓词」导致整条功能静默失效。**这次改之前先把
    现有三套集合（mineSeed / oppositeSeed / 实时集合）各自的语义写清楚**，
    再决定高能榜滚动窗口是第四套还是替换其中之一。

## P5-6 拉黑独立动作

- **4** 拉黑是**独立动作**，不是「禁言 720 小时」；拉黑规则与禁言规则**分开处理**
- 去掉禁言理由与昵称输入框：昵称由 UID 自动获取，理由无意义
- ⚠️ **账号级拉黑接口的参数尚未从真实报文验证过**。用户将用浏览器
  开发者工具抓「拉黑 / 取消拉黑」两条请求。**拿到真实报文之前不要动手**——
  本项目已经因为我把 C++ 里的死代码当成活路径写进研究文档，害实现者白做一版。
