## ⚠️ 写计划时发现的新缺口：统计页没有后端

设计文档 §13 列了六个前置缺口，**漏了这一个**。

统计页要展示「弹幕数、进房人数、礼物种类与数量、上舰数、直播时长、盲盒盈亏，按场次与按日两个维度」。而后端现在只有 `GET /api/bindings/{id}/activity`，返回**最多 500 条原始行**（`maxActivityLimit`）。

前端在 500 行上做聚合不是统计——一个活跃房间一天几万行，500 条连一个小时都盖不住，算出来的数字是错的，而且**不会报任何错**，只会显示一个看起来合理的小数字。

**这是 P5 的事还是 P4 的事，需要用户裁决。** Task 12 之前必须问。两个方向：

- **补一个聚合接口**（`GET /api/bindings/{id}/stats?by=day|session`），SQL 侧 `GROUP BY` 出来。工作量不大，但属于后端，要新开一个 P4-1 补丁任务
- **统计页这一版只做「最近 500 条能算出来的」**，并在页面上**显式说明**这是采样而非全量。诚实但价值有限

**不要默默在前端聚合 500 条然后当成全量展示**——那是三者里最差的，它给出一个错误的数字而不告诉任何人。

import { useEventStream } from './useEventStream'

/** 一个能手动喂消息的 EventSource 替身。 */
class FakeEventSource {
  static instances: FakeEventSource[] = []
  url: string
  onmessage: ((e: MessageEvent) => void) | null = null
  onerror: ((e: Event) => void) | null = null
  onopen: ((e: Event) => void) | null = null
  closed = false
  private listeners = new Map<string, ((e: MessageEvent) => void)[]>()

  constructor(url: string) {
    this.url = url
    FakeEventSource.instances.push(this)

    arr.push(fn)
    this.listeners.set(type, arr)
  }
  close() {
    this.closed = true
  }
  /** 测试用：模拟服务端推一条命名事件。 */
  emit(type: string, data: unknown) {
    const e = new MessageEvent(type, { data: JSON.stringify(data) })
    for (const fn of this.listeners.get(type) ?? []) fn(e)
  }
}

  beforeEach(() => {
    FakeEventSource.instances = []
    vi.stubGlobal('EventSource', FakeEventSource)
  })
  afterEach(() => {
    vi.unstubAllGlobals()
  })

  it('订阅的是这个绑定的流', () => {
    useEventStream(7)
    expect(FakeEventSource.instances[0].url).toContain('/api/bindings/7/stream')
  })

  // 后端推的是命名事件（event: danmaku\ndata: {...}），不是默认的 message

    const s = useEventStream(1)
    FakeEventSource.instances[0].emit('danmaku', { id: 'a', type: 'danmaku', payload: {} })
    expect(s.events.value).toHaveLength(1)
  })

  // 一个开着一整场直播的页面会收到几万条。不设上限的话内存一直涨，

  it('超过上限时丢掉最旧的，不是无限增长', () => {

    expect(es.closed).toBe(true)

    expect(s.events.value).toHaveLength(0)

- [ ] **Step 3: 实现 composable**

`web/src/composables/useEventStream.ts`：

```ts
import { onUnmounted, ref, shallowRef } from 'vue'

/** 推给浏览器的事件形状，与后端 streamEventView 对应。 */
export interface StreamEvent {
  id: string
  type: string
  roomId: string
  timestamp: string
  payload: unknown
}

/**
 * 后端会推的命名事件类型。
 *
 * SSE 的 onmessage 只接默认（未命名）事件，而后端每条都带
 * `event: <type>`，所以必须逐个 addEventListener——只写 onmessage
 * 的话一条都收不到，且不报任何错。
 */
const EVENT_TYPES = [
  'danmaku',
  'gift',
  'guard',
  'superchat',
  'enter',
  'follow',
  'share',
  'like',
  'battle',
  'live_start',
  'live_end',
  'manual',
  'unknown',
]

export interface EventStreamOptions {
  /** 内存里最多留多少条。 */
  max?: number
}

export function useEventStream(bindingId: number, opts: EventStreamOptions = {}) {
  const max = opts.max ?? 500
  // shallowRef：事件对象本身不会被改，不需要深响应，几万条的深代理很贵
  const events = shallowRef<StreamEvent[]>([])
  const connected = ref(false)
  const error = ref<string | null>(null)

  const es = new EventSource(`/api/bindings/${bindingId}/stream`)

  es.onopen = () => {
    connected.value = true
    error.value = null
  }
  es.onerror = () => {
    // EventSource 自带断线重连，这里只反映状态不主动重连——
    // 自己再实现一套重连会和浏览器内建的那套打架
    connected.value = false
    error.value = '实时连接断开，正在自动重连'
  }

  for (const type of EVENT_TYPES) {
    es.addEventListener(type, (e) => {
      let ev: StreamEvent
      try {
        ev = JSON.parse((e as MessageEvent).data) as StreamEvent
      } catch {
        return // 坏数据丢掉，不该让整个页面炸
      }
      // 新的在前，超出上限从尾部丢。一场直播几万条，不设上限的话
      // 内存一直涨，而用户只是把日志页开着没关
      const next = [ev, ...events.value]
      events.value = next.length > max ? next.slice(0, max) : next
    })
  }

  function close() {
    es.close()
    connected.value = false
  }

  onUnmounted(close)

  return { events, connected, error, close }
}
```

**注意上面测试里「留下的应当是最新的三条、`events.value[0].id === '2'`」**：实现是「新的在前」，所以喂 0..4 之后前三条是 4,3,2——`events.value[0].id` 是 `'4'` 不是 `'2'`。**测试和实现必须对齐，以哪个为准由实现者定，但要在报告里说明选了哪种顺序、为什么。** 日志页通常最新在上，所以「新的在前」更自然，那样测试要改成断言 `events.value[0].id === '4'` 且长度为 3。

结构：

- 顶部一排过滤器：`kind`（全部/事件/动作）、`eventType`（下拉，选项来自 `GET /api/meta/event-types`）、时间范围（`NDatePicker` 双选）、关键词（前端过滤，后端没有搜索参数）

## Task 8: 管理页（改密码、用户管理、授权管理）

**Files:**
- Create: `web/src/pages/Admin.vue`、`web/src/pages/Admin.test.ts`
- Create: `web/src/components/MemberEditor.vue`
- Modify: `web/src/router/index.ts`（加 `admin` 路由）

**Interfaces:**
- Consumes: `GET/POST/DELETE /api/users`、`POST /api/users/{name}/password`、`GET/PUT/DELETE /api/bindings/{id}/members`、`GET /api/meta/permissions`

**三块**：

1. **改自己的密码**（所有人）：旧密码 + 新密码。**自己改自己一律要带旧密码，管理员也不例外**——后端就是这么实现的（P4-1 Task 6 修过一次这里的授权分支顺序）
2. **用户管理**（仅管理员）：列表、新建、删除、重置他人密码（管理员改**他人**密码不需要旧密码）
3. **授权管理**（对当前绑定有 `member:manage` 的人）：谁能碰这个绑定、各有哪些权限点

**权限预设在这里展开**（设计文档 §7.3）：

```ts
const PRESETS: Record<string, Permission[]> = {
  运营: ['rule:read', 'rule:write', 'event:read'],
  房管: ['user:block', 'event:read'],
  观察: ['rule:read', 'event:read'],
}
```

按钮只是一键勾选一组复选框，**提交给后端的永远是展开后的权限点数组**。存储层只有权限点，没有角色。

**两条容易做错的**：

1. **`account:manage` 已经被删掉了**（用户裁决，权限点从七个变六个）。权限点清单**必须从 `GET /api/meta/permissions` 拉**，不要在前端硬编码——硬编码就是第二处定义，后端再改一次就漂了
2. **账号所有者拿不到自己绑定上的 `member:manage`**（这是刻意的，见 P4 设计文档 §4.2）。所以「我是账号所有者但打不开授权管理」是**正常现象**，不是 bug。界面上要说清：缺 `member:manage` 时显示「授权管理需要 member:manage 权限，请让管理员授予」，**不要**写成「你不是所有者」

## Task 9: 弹幕姬（上）——进房欢迎与礼物答谢

**这一页的本质：它是规则编辑器的「傻瓜模式」。** 每个功能块（进房欢迎、礼物答谢……）在后端就是一条规则，前端把它渲染成一组开关与输入框，保存时组装成 `spec.Rule` 写进 `PUT /api/bindings/{id}/rules`。

**先写 `rule-types.ts`**，对应后端 `server/internal/rules/spec/spec.go` 的 `Rule`/`Condition`/`Aggregate`/`Action`。**逐字段照着 Go 结构体的 json tag 写**，Task 2 的教训是「抄计划不抄代码就会漂」。

**功能块与规则的对应**（每块一条规则，`name` 固定，前端靠 `name` 认领）：

| 功能块 | 规则 name | on | 关键字段 |
|---|---|---|---|
| 进房欢迎 | `内置/进房欢迎` | `enter` | `aggregate`（合并窗口）、`when`（粉丝牌筛选）、`do`（弹幕模板） |
| 礼物答谢 | `内置/礼物答谢` | `gift` | 同上 |

**四处悬空，都要标「待后端支持」**：

1. **粉丝牌判定口径**（设计文档 §13.2）：「进房一瞬间有亮起的主播粉丝牌才算佩戴」。后端的 `Enter` 事件目前没有这个字段，条件写不出来
2. **模板轮询模式**（§13.3）：当前规则引擎只有随机抽取。界面上「轮询/随机」二选一的单选框可以渲染，但选「轮询」暂时不生效
3. **单人/多人两套模板**（§13.3）：当前一条规则只有一套 `Template`。界面上分两栏，但保存时只有单人那套生效
4. **盲盒单列**（§13.4）：礼物答谢里「盲盒礼物单独一类」的开关先悬空

**保存走 Task 13 的统一机制**，本任务只管把草稿状态做出来（改动进内存、`dirty` 变真），不自己调保存。

## Task 13: 保存与热重载的统一交互

**Files:**
- Create: `web/src/composables/useDraft.ts`、`useDraft.test.ts`
- Modify: 弹幕姬、自定义弹幕姬、房管（有草稿态的页面）

**用户的要求**：

> 右上角设置一个保存按键，当设置被更改以后按下保存才生效。

`useDraft` 封装三件事：

1. 草稿与已保存值的比较 → `dirty`
2. 保存流程：`PUT` 写库 → `POST /api/bindings/{id}/reload` → 成功后 `dirty` 归假
3. **离开拦截**：`onBeforeRouteLeave` + `beforeunload`

**重载失败要显示具体原因。** 后端对规则非法返回 422，文案形如「重载失败，仍在用上一份配置运行: 规则 X 的正则非法」——**「仍在用上一份配置运行」这句是操作者最需要的安抚**，别丢掉。
